# Chat Templates Illustrated: Curriculum and Project Plan

## Project thesis

A base model and an instruction-tuned chat model both generate tokens autoregressively. What changes is the training that shaped their likely continuations, the special-token conventions used to serialize context, and the host software that decides when to stop or ask the model to continue.

The project should let learners manipulate those layers separately. Every lesson must expose a mechanism in the lab rather than relying on explanatory copy alone.

## Audience and learning goals

The primary audience is a curious non-specialist who has used a chatbot but has not worked with tokenizers or inference harnesses. The writing should remain accessible to a middle-school learner while using precise terms that support deeper discussion.

By the end of the core series, a learner should be able to explain that:

- A base model continues a token sequence; it has not been trained specifically to behave like a helpful conversational partner.
- Instruction tuning changes which continuations are likely, not the underlying next-token generation mechanism.
- Chat bubbles are an interface over one serialized sequence containing message content, role markers, and turn boundaries.
- Special tokens are reserved vocabulary entries whose behavior was learned during training. They are not commands with universal meanings.
- End-of-sequence (EOS) and end-of-turn (EOT) are related but not interchangeable. A host may treat several tokens as end-of-generation conditions.
- A model can predict text for a user turn as well as an assistant turn when the serialized prefix asks it to continue that role.
- Conversation history is normally rebuilt into the next prompt. It is context, not permanent memory or retraining.
- Host software, not the model, owns stopping, cancellation, context assembly, and generation limits.

## Core interactive lab

The main screen should be the usable lab, not a marketing page. Keep the visual language of `StatisticalNatureOfLLMs`: warm paper and white surfaces, dark ink, green/coral/yellow accents, editorial serif headings, compact technical labels, square-edged controls, lesson callouts, and responsive desktop/mobile layouts.

Replace the earlier story tree with four synchronized views:

1. **Conversation**: editable system, user, and assistant messages shown as a traditional chat log.
2. **Serialized sequence**: the exact rendered template with ordinary text, role markers, boundary markers, and the generation prompt visually distinguished.
3. **Generation timeline**: generated text plus stop events, finish reason, and which actor made each decision (model or host).
4. **Harness controls**: model, template mode, stopping policy, seed, temperature, and a context-length meter.

Selecting a message or marker in one view should highlight its representation in the others. A persistent legend should distinguish:

- ordinary text supplied by a person or application;
- ordinary text generated by the model;
- reserved/special tokens;
- host-only events that are not tokens;
- content hidden by the chat UI but present in model context.

The lab needs two operating modes:

- **Guided mode** runs deterministic lesson presets and opens focused callouts.
- **Sandbox mode** lets learners edit messages, templates, and stop behavior after completing or dismissing a preset.

## Core lesson sequence (MVP)

### 1. A chatbot is still a next-token model

**Thesis:** Base and instruction-tuned checkpoints use the same autoregressive mechanism, but post-training changes which continuations they make likely.

**Experiment:** Run a matched base/instruct pair on three controlled inputs: a plain document prefix, a bare instruction, and a correctly templated user message. Hold seed and decoding settings fixed. Compare the serialized input, first-token candidates, and short continuation.

**Guardrail:** Do not imply that the base model is broken or that the instruct model contains a separate question-answering engine.

### 2. Chat bubbles become one sequence

**Thesis:** Structured messages are serialized into one ordered token sequence before inference.

**Experiment:** Build a two-turn conversation one message at a time. Animate each bubble into the corresponding role marker, content, and boundary marker in the sequence view. Toggle between raw completion and the model's expected chat template.

**What should be visible:** The generation prompt ends with an assistant-role marker but no assistant content, making “continue as the assistant” a property of the prefix.

### 3. Special tokens are learned markers, not magic commands

**Thesis:** A reserved marker matters because the tokenizer recognizes it and training taught the model patterns around it; its spelling has no universal power.

**Experiment:** Starting from a working chat template, remove one role marker, replace it with ordinary text, and swap user/assistant markers. Compare the next-token distribution and continuation after each change.

**Guardrail:** Label model-family-specific syntax as an example, never as the universal format used by all LLMs.

### 4. The model proposes an ending; the harness stops

**Thesis:** The model can predict an end-of-generation token, while host software decides what that prediction means for the running application.

**Experiment:** Generate normally and pause when an EOT or EOS token is selected. Show the token prediction and the separate host event that stops generation. Then enable “ignore end marker” and continue for a tightly capped number of tokens.

**What learners should notice:** Continuing may begin another role, repeat a boundary, or produce incoherent text. It is an experiment in learned continuation patterns, not a reliable hidden-response mode.

**Safety limit:** The override must have a small hard token cap, a visible cancel action, and no automatic continuation loop.

### 5. Conversation history is the next prompt

**Thesis:** On each turn, the application normally sends the prior messages again as context. The model conditions its next response on that transcript; it does not verify that the transcript is true, remember privately producing its earlier messages, or retrain itself.

**Experiment:** Begin with an editable, pre-filled transcript:

- User: “What is the moon made out of?”
- Assistant: “The moon is made of cake.”
- User: “That's obviously wrong. Why do you think you answered in that way? Diagnose and explain how your reasoning produced that incorrect answer.”

Ask the model to continue as the assistant. It may invent a plausible-sounding retrospective explanation for an answer that the application inserted and the model never generated. Let the learner edit the false answer, switch to a second preset about planes flying through factory wizardry, and write their own replacement. Regenerate the explanation after each edit while keeping model, seed, and decoding settings fixed.

Then compare four conditions:

1. The full transcript, including the false assistant answer.
2. The same transcript with the false answer replaced by a correct one.
3. The follow-up question without the earlier exchange.
4. A clean conversation asking the original factual question directly.

**What learners should notice:** The serialized sequence presents the earlier assistant message as context, regardless of who actually wrote it. The new response can rationalize that context, but the rationalization is newly generated text, not a readout of the causal process that produced the alleged earlier answer.

**Interface requirements:** Visually label each message as “preset,” “edited by you,” or “generated now.” Keep the complete serialized history visible and make the context meter show that old turns consume the same finite sequence budget as new text.

**Guardrail:** Do not summarize this as “the model believes the history is true.” More precisely, the model is conditioned on a sequence formatted as conversation history and has learned to continue such sequences coherently. Its output alone cannot establish belief, memory, or faithful introspection.

### 6. The model can continue either side of the transcript

**Thesis:** Next-token prediction is not inherently restricted to assistant prose. With a prefix ending in a user-role marker, the model can generate a plausible next user turn.

**Experiment:** After a completed assistant response, append the normal turn boundary and a user-role generation prefix, then generate a short “predicted user” continuation. Compare it with free-running generation after an ignored stop marker.

**Guardrails:** Describe the result as a likely textual continuation conditioned on this transcript, not a prediction of what the real user intends or will do. A tiny model may produce weak results; presets must be selected from reproducible examples rather than promising a particular behavior for arbitrary chats.

## Model strategy

### MVP pair

Use quantized **SmolLM2 135M Base** and **SmolLM2 135M Instruct** checkpoints from the same family. The base model is already used by the sibling project at roughly 92 MB in Q4, and the matched instruct checkpoint is small enough for the same browser-first experience. The published model lineage explicitly identifies the instruct model as a fine-tune of the base model.

This pair is suitable for serialization, role, stopping, history, and base-vs-instruct lessons.

### Optional stronger comparison

Evaluate Qwen2.5 0.5B Base/Instruct as an opt-in “stronger example” after the MVP. It is a matched Apache-2.0 pair with an embedded chat template and better instruction behavior, but Q4 downloads are likely several hundred megabytes per checkpoint. Never require both models to be resident simultaneously.

## Technical architecture and constraints

- React, TypeScript, Vite, and `@wllama/wllama`, matching the sibling project.
- Static GitHub Pages deployment from a GitHub Actions build; no server, proxy, database, telemetry, or inference API.
- Models remain hosted on Hugging Face and are downloaded on demand into browser OPFS cache.
- Bundle the single-thread WASM runtime because project Pages cannot set the cross-origin isolation headers required by multithreaded WASM.
- Prefer WebGPU opportunistically only after testing; the single-thread WASM path remains the compatibility baseline.
- Keep context deliberately small for fast lessons and make truncation explicit rather than silently dropping messages.
- Store only UI preferences and lesson progress locally. Conversation text stays in memory unless the learner explicitly exports it.
- Provide loading progress, cancel generation, cache size/clear controls, reduced-motion behavior, keyboard focus states, and mobile layouts from the first release.

### Inference boundary

Use raw completion when the lesson needs to show or alter the rendered template. Use chat completion only as a comparison to demonstrate what a convenience API normally assembles. Record a timeline event for every host decision.

wllama v3 currently provides model metadata for BOS, EOS, EOT, end-of-generation token IDs, finish reasons, raw completion, chat completion, `ignore_eos`, and embedded Jinja chat templates. It does not expose the old public `tokenize`/`detokenize` methods. Therefore exact prompt token IDs and boundaries require a feasibility spike rather than being an MVP promise.

Possible token-inspection paths, in order of preference:

1. Verify whether wllama response metadata or a newer compatible release can return prompt token details.
2. Use a lightweight tokenizer implementation that is guaranteed to match the selected GGUF vocabulary and special-token configuration.
3. Display exact rendered special markers plus model-reported prompt-token counts, while limiting per-token inspection to generated tokens returned in logprobs.

The UI must label which level of fidelity it is showing. Never infer token IDs by splitting strings.

## Delivery milestones

### Milestone 0: feasibility spike

- Verify the exact Q4 GGUF URLs, licenses, CORS behavior, embedded templates, special tokens, and download sizes for the SmolLM2 pair.
- Capture the rendered template and stopping behavior through wllama on Chrome, Firefox, and Safari.
- Test whether `ignore_eos` suppresses every relevant end-of-generation token or EOS only; name the UI control according to observed behavior.
- Find deterministic presets for all six lessons.
- Decide the token-inspection fidelity and document any limitation in the UI.

**Exit criterion:** A plain prototype can load each model, run raw and chat completion, visibly stop on a boundary, continue under a capped override, and reproduce the guided examples.

### Milestone 1: lab shell

- Build the synchronized conversation, sequence, timeline, and harness views.
- Add model download/cache management and responsive accessibility states.
- Add URL-addressable lesson definitions and the guided preset/callout system.

### Milestone 2: core curriculum

- Implement and validate lessons 1-3.
- Implement and validate lessons 4-6.
- Add learner-facing limitations, privacy copy, sources, and model credits.
- Test mobile and desktop layouts and run the production build/lint checks.

## Acceptance criteria

- Every thesis has a deterministic, learner-controlled experiment.
- The base/instruct comparison uses checkpoints from one documented model lineage.
- The interface never conflates text, special tokens, and host events.
- EOS, EOT, stop strings, maximum-token limits, and user cancellation are distinguishable when applicable.
- “Predict the user” copy avoids claims about reading intent or forecasting a real person's behavior.
- The false-history lesson distinguishes preset or learner-edited assistant text from text generated during the current run.
- Retrospective explanations are described as new conditioned continuations, not faithful access to hidden reasoning.
- Reloading after a cached download works without redownloading under normal browser storage conditions.
- The core lessons remain usable on a phone and on a device without WebGPU.
- GitHub Pages hosts the complete application with no runtime backend.

## Explicit non-goals for the first release

- Training or fine-tuning models in the browser.
- Comparing many unrelated model families.
- Reverse-engineering hidden reasoning or internal activations.
- Claiming special-token formats are standardized across models.
- Tool calling, agents, retrieval, memory databases, or network browsing. Those belong in a separate curriculum series.
- Exact token-level prompt inspection unless the feasibility spike proves it can be faithful to the loaded GGUF.

## Recommended scope decision

Ship the six-lesson curriculum as one focused series. It forms a coherent conceptual arc: continuation, post-training, serialization, markers, stopping, replayed history, and role-conditioned generation. Tool calling and agents are intentionally reserved for a separate future project.
